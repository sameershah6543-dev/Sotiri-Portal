# MCC Sending Manifest — Build Context

This file is the complete brief for building a **live, standalone web app** version of the
"Sending Manifest" portal — a single-account command center for MailClickConvert's (MCC)
email-sending operations, meant to be built with Claude Code, deployed on Vercel, and shared
with both the internal team and the client.

Drop this file into your project folder, open Claude Code in that folder, and tell it to read
this file first. It contains: what the product is, who uses it, the exact data model, the
underlying platform API this pulls from (and its known landmines), the visual design system
already validated with the user, and a suggested build plan. It does **not** contain a live API
key — see "API access" below for why, and what you need to do about it.

---

## 1. What this is and why it exists

MCC runs email campaigns for multiple businesses (fuel/petroleum distributors, mostly — e.g.
"Gaubert Oil," "Beck Oil," "ED STAUB & SONS") through one email-sending platform account. Each
campaign sends from a specific domain + IP ("sending profile"). Over the course of an audit
(Aug–Sep 2026) we found and fixed real problems that had already caused a client complaint:
campaigns with no sending profile at all, campaigns whose sending domain didn't match the
business name, 18 domains that were missing outright and had to be purchased and provisioned
from scratch, and one platform API bug that accidentally flipped HTTPS on 41 domains
account-wide (documented below — do not repeat it).

The client's complaint landed **before** the team noticed the problem. The point of this portal
is to flip that: surface expiring domains, blacklisted (SBL/DBL) domains, missing sending
profiles, and mismatched domain/campaign pairings automatically, so the team catches it first.

We already built a first version of this as a self-published Claude Artifact (a single static
HTML page with an embedded JSON snapshot, manually republished to refresh). That version proved
the data model and the UI design and is the reference for this build — the goal now is a "real"
app: its own repo, a real database for the parts that need to persist (flags, notes, replacement
log), a scheduled job that refreshes platform data automatically, and a URL on Vercel that both
the team and the client can be given access to.

## 2. Who uses it and what they can do

Two roles:

- **Team (edit access).** Can see everything, and can: flag a domain as SBL/DBL-listed or clear
  a flag, log a domain replacement (old domain → new domain, reason, date), and add free-text
  notes to a domain or campaign. There is no in-app blacklist checking — SBL/DBL status is
  entered manually by a person who checked Spamhaus (or wherever) themselves. This was an
  explicit decision: automatic blacklist checking was considered and declined.
- **Client (view-only).** Sees the same data — their own account's campaigns, domains, and
  replacement history — but cannot flag, log, or edit anything. No write controls should even
  render for this role.

Keep this to a simple role gate (e.g. a shared team password/token vs. a shared client
link/token, or a short allow-list of emails if you wire up real auth) — this does not need
per-user accounts or a client CRM. There is no formal "clients" object in the underlying
platform (its API returned zero client records when queried) — "client" here just means the
business name embedded in each campaign's title, e.g. "CFN 06 Beck Oil" → client "Beck Oil".

Refresh cadence: platform data is a **snapshot refreshed a few times a day**, not live-per-load.
This was explicit — the user does not want every page load hitting the platform API. A scheduled
job (Vercel Cron) should pull fresh campaign/domain/profile data on a fixed schedule (suggest
every 4–6 hours) and merge it into the stored snapshot, described in section 5.

## 3. Data model

This is the exact shape validated in the working prototype. `campaigns`, `domains`,
`replacements`, and `unusedProfiles` are refreshed from the platform API on each scheduled pull.
`notes` (and the `sbl`/`dbl`/flag fields nested in `domains`/`campaigns`) are **manually entered
and must survive every refresh** — the refresh job must merge, never overwrite, these fields.

```ts
type State = {
  clientName: string;          // "MailClickConvert"
  lastRefreshed: string;       // ISO 8601 timestamp of the last successful platform pull

  campaigns: Array<{
    id: string;                // platform campaign id, e.g. "140905"
    title: string;             // e.g. "CFN 05 Gaubert Oil" — client name is embedded here
    status: "Pending" | "Paused" | "Completed";
    profileId: string | null;  // sending profile id currently assigned
    domain: string;            // sending domain this campaign actually rotates through —
                                // MUST be cross-checked against BOTH profileid and
                                // rotatedprofiles.profile.profileid on the platform (see §4)
    https: boolean;
    dmarc: string;              // e.g. "reject"
    sbl: boolean;               // manually flagged, not auto-checked
    isNewDomain: boolean;       // true for the 18 domains bought during the 2026 audit
  }>;

  domains: Array<{
    domain: string;
    domainId: string;
    status: string;             // e.g. "Domain Ready"
    https: boolean;
    dmarc: string;
    expireDate: string;         // "YYYY-MM-DD"
    daysLeft: number;           // derived at render time from expireDate, not stored — but
                                 // keeping it here in the reference shape for clarity
    renew: "Yes" | "No";        // registrar auto-renew flag
    hasProfile: boolean;
    profileId: string | null;
    ip: string | null;
    usedByCampaigns: string[];  // campaign ids currently sending from this domain
    sbl: boolean;               // manual flag
    dbl: boolean;                // manual flag
    originalNote: string | null; // free text, e.g. why a domain was replaced
  }>;

  replacements: Array<{
    newDomain: string;
    oldDomain: string;
    client: string;
    campaignTitle: string;
    campaignId: string;
    reason: string;              // e.g. "missing - never existed in account"
    date: string;                // "YYYY-MM-DD"
  }>;

  unusedProfiles: Array<{        // sending profiles that exist but aren't assigned to any campaign
    profileId: string;
    domain: string;
    ip: string;
  }>;

  notes: Array<{
    ts: string;                  // ISO timestamp
    author: string;              // free text name, e.g. "Momo"
    type: "sbl-on" | "sbl-off" | "dbl-on" | "dbl-off" | "note" | "replacement";
    target: string;              // domain name, or "oldDomain → newDomain" for replacements
    text: string;                // free text reason/note
  }>;
};
```

Derived, not stored (compute these client-side or in an API route, always from live state, never
cached): days-until-expiry per domain, an "attention" list (critical: SBL/DBL-flagged domains,
campaigns with no `profileId`, campaigns on an SBL-flagged domain; warning: domains expiring
within 60 days), and summary counts for the gauge strip (campaigns in flight, flagged domains,
expiring-soon count, HTTPS coverage %, spare/unassigned profile count).

**Known current data, as of this writing** (useful as realistic seed data — do not treat as
static, it will drift): 179 campaigns (177 pending, 2 paused), 193 domains, 108/193 domains have
HTTPS on (56%), 15 sending profiles built but not assigned to any campaign, 18 domains logged as
replacements from the 2026 audit. 24 domains expire in ~41 days (around 2026-10-13, apparently a
batch registered on a one-year term) — 23 of those have auto-renew on and are fine; one,
`jacksonoilsolventsinc.com`, has auto-renew off but is currently unused by any campaign, so
letting it lapse is safe, not urgent. The account itself: billing period Aug 28–Sep 28 2026,
400,000 email package size, ~5,378 sent this cycle, 154 total IPs, 0 complaints.

The full current snapshot is attached as seed data in Appendix A — use it to seed your database
so the app has real data from the first deploy, instead of an empty shell.

## 4. The underlying platform API

The account is on a white-label email-sending platform (referred to throughout as "MCC" — this
is the account MailClickConvert uses to run these campaigns). Its API is organized as
`area` + `action` pairs, each with an HTTP method (GET for reads, POST for writes). The areas
relevant here all live under `email` (90 actions total on that area; other areas on the account —
`sms`, `leads`, `listverify`, `datafinder`, `data`, `support`, `home`, `ai`, `clients`, `api` —
are not used by this portal). The actions this build actually needs:

| Action | Method | Purpose |
|---|---|---|
| `email/getcampaigns` | GET | list all campaigns (id, title, status, profileid, domain, etc.) |
| `email/getcampaigndetail` | GET | full detail for one campaign, incl. `rotatedprofiles.profile.profileid` |
| `email/getsendingprofiles` | GET | list all sending profiles (id, domain, ip, serverid, https, datecreated) |
| `email/getdomains` | GET | list all domains (id, domain, status, https, dmarc, expiredateiso, monitorenabled) |
| `email/getips` | GET | list all IPs (id, ipaddress, status, shareable, reversednsdomain, serverid) |
| `email/editcampaign` | POST | reassign a campaign's sending profile |
| `email/addprofile` | POST | create a new sending profile (params: `domainid`, `ipid`, `serverid`, `https`) |
| `email/getaccountinfo` | GET | billing period, package size, totals — good for the account-level gauges |

**Two hard-won landmines, both must be respected by any new integration code:**

1. **The rotation dual-field bug.** A campaign's `profileid` field can look correct while a
   separate field, `rotatedprofiles.profile.profileid`, still points at the wrong/old profile —
   this field actually controls what the campaign sends from. Any code that reassigns a
   campaign's sending profile must set `profileid`, `rotatedprofiles`, `rotateprofiles`, AND
   `profilerotation` all to the same target profile id in the same `editcampaign` call, and any
   code that reads/audits a campaign's assignment must check both fields and flag a mismatch.
2. **`email/updatedomainsettings` is account-wide-buggy.** Calling it to change one domain's
   HTTPS or monitoring setting ignores the target `domainid` and applies the change to **every**
   domain on the account. This was discovered the hard way (flipped HTTPS on 41 unrelated
   domains). Do not call this action from the new app at all unless the platform vendor confirms
   it's been fixed — if HTTPS/monitoring toggles are needed in the UI, make them a manual
   checklist item for a human to do in the platform's own dashboard, not an automated API call.

### API access — you need to get the real key yourself

I don't have the platform's raw API key or its exact base-URL/auth format to hand you. In this
Claude session, I reach the MCC platform through a pre-authenticated connector — it lets me call
`area`/`action` pairs, but it does not expose the underlying secret or endpoint URL to me as
plain text, so there is nothing for me to copy into this file even though I asked myself the same
question.

What to do: log into the MCC platform's own web dashboard and look for an API/Developer/
Integrations settings page (the account does have an `api` area with webhook-management actions —
`addwebhook`/`getwebhooks`/`deletewebhook` — which is a good hint that there's a
credentials/integrations section in that same part of the UI). Generate or copy the account's API
key there, along with the exact base URL and whether the key goes in a header or a query
parameter — every platform in this category does it slightly differently, so check the
platform's own API docs page rather than assuming.

Once you have it:

- Local dev: put it in `.env.local` as `MCC_API_KEY=...` and `MCC_API_BASE_URL=...`. Make sure
  `.env.local` is in `.gitignore` (Next.js does this by default) — never commit it.
- Production: add the same two values in the Vercel project's Settings → Environment Variables,
  not in any file that gets committed.
- Never put the real key in this markdown file, in a seed file, or in any client-side code —
  all platform calls must go through server-side API routes (Next.js Route Handlers), never
  fetched directly from the browser.

## 5. Suggested architecture

- **Next.js (App Router) + TypeScript, deployed on Vercel.** Matches the "live in Claude Code
  terminal, live on Vercel" ask directly.
- **A small database for the persistent, manually-entered parts**: the `notes` list, and the
  `sbl`/`dbl` flags and replacement log entries. Vercel Postgres or a free Neon/Supabase Postgres
  instance both work fine at this scale (hundreds of rows). Don't put the manually-entered data
  in the same table as the platform snapshot — keep a `platform_snapshot` table/row (overwritten
  on every refresh) and a `manual_overrides` table (flags, notes, replacements — never
  overwritten by a refresh, only appended/updated by user actions).
- **A scheduled refresh job**: a Vercel Cron Job hitting an internal API route (e.g.
  `/api/refresh`, protected by a secret so only the cron can call it) a few times a day. It
  pulls fresh `getcampaigns`/`getcampaigndetail`/`getsendingprofiles`/`getdomains`/`getips`,
  rebuilds the `platform_snapshot`, and re-derives `hasProfile`/`usedByCampaigns`/mismatch
  detection — but leaves every row in `manual_overrides` untouched. The page always renders
  `platform_snapshot` merged with `manual_overrides` at request time (or on a short revalidation
  window), never a stale mix baked in at cron time.
- **Two write API routes**, both team-only: `/api/flag` (set/clear `sbl`/`dbl` on a domain, or
  add a free-text note) and `/api/replacement` (log a domain replacement). Both append a row to
  `notes` too, so the Activity tab has a full audit trail.
- **Role gate**: simplest viable approach is two shared links/tokens — a team link that sets an
  edit-cookie, and a client link that doesn't. If the project already has a real auth provider in
  mind, that works too, but don't over-build this — two roles, no per-user accounts needed.

### Pages

- `/` — overview: the gauge strip + "needs attention" list (the two things a person should see
  in the first five seconds).
- `/campaigns` — full campaign table: title, status, sending domain, profile id, HTTPS, DMARC,
  flags. Searchable.
- `/domains` — full domain table: status, HTTPS, DMARC, expiry + days-left, auto-renew, assigned
  profile/IP, SBL/DBL flags, "issues only" filter.
- `/replacements` — the replacement log (old domain → new domain, client, reason, date).
- `/activity` — the `notes` feed, newest first — this is the audit trail of every manual action
  taken in the portal.

## 6. Design system (already validated with the client — reuse exactly)

The prototype's visual design was reviewed and approved. Reuse these tokens rather than
reinventing them.

**Palette** (light theme; dark theme is the same role, inverted — see the CSS variables below for
exact dark values):

- `--paper #EEF3F1` — page background
- `--surface #FFFFFF` / `--surface-2 #E3EAE7` — card and table backgrounds
- `--ink #10171A` / `--muted #5B6A67` — text
- `--line #C9D2CF` — borders/dividers
- `--accent #1B6B72` / `--accent-strong #124D52` / `--accent-soft #DCEBEA` — teal, the one accent
  hue (used for the active tab, links, focus states — not repeated everywhere)
- `--good #256B41` / `--warn #9A6205` / `--critical #A5322A` (each with a `-soft` background
  tint) — semantic status colors, kept separate from the accent hue

Dark theme swaps to: `--paper #0C1214`, `--surface #121A1C`, `--surface-2 #182120`,
`--ink #E7ECEA`, `--muted #93A29E`, `--line #263230`, `--accent #4FA8AE`,
`--accent-strong #79CBD0`, `--accent-soft #17302E`, `--good #5DBB89`, `--warn #E0A93B`,
`--critical #E2695C` (each with its own `-soft` tint). Support all three theme states properly:
an explicit light/dark toggle, and the OS-level `prefers-color-scheme` default — don't just do
light mode.

**Type**: Barlow Condensed (600/700) for display/headings, IBM Plex Sans (400/500/600) for body
text and UI, IBM Plex Mono (400/500) for ids, domains, and anything tabular/numeric. All three
load fine from Google Fonts.

**Layout concept**: a "control-room manifest" — a top gauge strip of small stat tiles, a sticky
left-hand "needs attention" rail (the triage list — what to look at first), and a large tabbed
table area on the right (Campaigns / Domains & profiles / Replacement log / Activity). Status is
always encoded redundantly — color chip + text label, never color alone. Search boxes filter each
table client-side; an "issues only" checkbox on the Domains tab hides anything with no problems.

## 7. Build plan

1. Scaffold Next.js + TypeScript + Tailwind, wire up the Postgres connection and the two tables
   (`platform_snapshot`, `manual_overrides`/`notes`).
2. Load Appendix A's JSON as the initial seed so the four pages have real data immediately.
3. Build the four pages + overview against the seed data, matching the design system above.
4. Build `/api/flag` and `/api/replacement`, wire the role gate so only team access shows the
   controls.
5. Build `/api/refresh` (the platform pull + merge logic), protect it, wire up Vercel Cron.
6. Once a real API key is in hand (§4), point `/api/refresh` at the real platform and confirm one
   live pull matches the seed data's shape.
7. Deploy to Vercel, generate the team link and the client link, confirm the client link truly
   has no write controls.
